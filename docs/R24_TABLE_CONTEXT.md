# R24.6 — Single restaurant table and order context
The local adapter derives table code from the existing validated QR registry and profile from the current sample membership. A visit and guest identity are independently generated per tab session and expire after four hours. Table/profile changes and sign-out rotate identity. New conversation rotates only the conversation ID; earlier messages remain staff history. Reload retains the current visit. The demo cannot establish real identity or detect a new person who takes over an unlocked tab without signing out; tab duplication and developer tools are not security boundaries.
New local table orders store tableCode and connectVisitId when chat storage is available. Only the latest order from that exact active profile, table and visit is associated; older orders and other tables are excluded. The core link_order operation checks actor/state; the adapter checks the relationship. Order linking does not block successful ordering, and later read reconciles if the first link fails. Closed/resolved conversations are not relinked. No migration of old orders without visit metadata.
Staff inbox shows table code and associated order items without member names/phones. Search supports table code and order ID. Legacy single-scope database identifiers remain for backward compatibility. No real backend changes, signed guest authorization, or database schema migration in this stage. Browser and CI tests remain required before release.
