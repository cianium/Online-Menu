# R26 — unified phone entry (connected Fastify candidate)
Owner requirement: one phone-first screen for customers and staff. Existing verified number → OTP; new number → name → OTP. Staff enrollment additionally requires a phone-bound, expiring, one-time operator-issued key. Only server membership determines the destination; a customer cannot gain staff access by selecting a role.
 
## Current implementation and safety boundary
The Fastify backend now has opt-in phone-auth endpoints and a new local migration. The provider adapter is a **contract**, not a claimed connection to an existing SMS service. No credentials are committed, no real message was sent, no production migration was applied. Supabase hosted commerce uses a distinct Auth broker and must be integrated separately before any hosted OTP rollout. Standalone GitHub Pages has no trusted backend and must remain sample-only; do not ask users to provide real numbers there.

- `GET /api/v1/auth/phone/status`: returns enabled capability.
- `POST /api/v1/auth/phone/lookup`: phone, returns needsName (no role, ID, or name); this requested UX exposes registration existence, so rate limit and monitor it. 
- `POST /api/v1/auth/phone/start`: phone, name when new; rejects any accessKey. `POST /api/v1/auth/phone/enroll-admin`: phone, name and mandatory accessKey; separate staff enrollment. Returns opaque challenge after SMS adapter acceptance. Code is never returned in the API.
- `POST /api/v1/auth/phone/verify`: challenge and six-digit code. Server creates identity and consumes invitation only on successful verification, rotates session/CSRF cookies and derives destination role from memberships.
- All POST routes use existing CSRF protection; credentials are server-owned. Codes expire in 5 minutes, 5 failures maximum, 60-second cooldown, database-backed per-phone and per-IP limits. Previous challenge is invalidated before resend. No plaintext codes/keys stored. Enrolled staff receive manager role, not owner, preserving least privilege. Existing accounts cannot self-upgrade via invite. Existing staff accounts require a separate verified phone-binding migration, not automatic assignment based on unverified input.

## Configuration (not enabled by default)
Apply local migration in isolated staging first. Set PHONE_AUTH_SECRET to a high-entropy secret, PHONE_AUTH_SMS_URL to a trusted HTTPS adapter, PHONE_AUTH_SMS_TOKEN to its credential. Adapter accepts POST JSON {phone,code,purpose,expiresIn}, bearer authentication, returns 2xx only when accepted for delivery. Configure the adapter to use the actual SMS provider; no provider assumed. Run `npm --prefix backend run auth:invite -- +989xxxxxxxxx restaurant-slug` as trusted operator; securely deliver the printed key only to the intended person. Expiry 24 hours. Schedule retention: delete expired challenges older than 24 hours, unused/used expired invites after challenge cleanup, and limits older than 24 hours; define deployment-specific retention and audit before activation. 
 PHONE_AUTH_ENABLED remains false. Legacy password sign-in remains available while disabled. When enabled, it is disabled unless PHONE_AUTH_LEGACY_PASSWORD=true is explicitly set during recovery/migration. Do not enable before owner phone verification, actual provider test, integration tests (concurrency, replay, throttling, role isolation, CSRF, session and logout), and hosted parity where applicable.

## Shared connected UI
When the local capability is enabled, an unauthenticated /admin/ request redirects to the same customer-side full-screen entry (login=1). A public QR entry and the customer profile can open the same component. Existing number goes to OTP; new number goes to the customer-only registration form. A separate admin registration view requires phone, name and access key. Returning staff use the shared phone-only login. Only verified response role selects dashboard vs restaurant. Form copy is available in four locales. No credentials are placed in URLs or browser storage. Demo retains its existing explicitly fictional entry until a dedicated simulation of the new flow is built and tested. No SMS, live service or database migration is performed by static Pages.

The CI phone-auth-contract job runs the new Fastify migration and actual HTTP route/cookie/authorization tests against a disposable PostgreSQL 17 instance with an in-process mock SMS adapter. This does not validate delivery to a real handset or hosted Supabase Auth.
