# مرحله نهم — آماده‌سازی Demo تجاری و VPS

این سند برای بررسی محصول پیش از نصب روی VPS است. هیچ سرور، دامنه، دیتابیس یا سرویس انتشار در این مرحله نصب/تغییر نمی‌شود.

## مسیر اول: بررسی محلی (بدون Backend)

Node.js 22 کافی است. از ریشه مخزن `npm run demo` را اجرا کنید و دو آدرس `http://127.0.0.1:8765/` و `http://127.0.0.1:8765/admin/` را در یک پروفایل مرورگر باز کنید. اطلاعات نمایشی در localStorage همان origin و مرورگر ذخیره می‌شوند؛ بین دستگاه‌ها یا مشتریان همگام نمی‌شوند. اطلاعات واقعی مشتری، رمز عبور یا داده حساس در Demo وارد نکنید.

## مسیر دوم: ساخت بسته جداگانه برای نصب آینده

```sh
npm run qa
npm run demo:export
cd dist/demo/public
sha256sum -c ../SHA256SUMS
```

خروجی به صورت `dist/demo/public` و فایل `dist/demo/SHA256SUMS` است. فقط `public` ریشه وب‌سرور خواهد بود. فایل checksum خارج از ریشه عمومی باقی می‌ماند. خروجی موجود عمداً بازنویسی نمی‌شود؛ برای نسخه بعدی مسیر تازه‌ای با والد موجود انتخاب کنید: `npm run demo:export -- /path/to/new-bundle`. محتوا از مسیرهای عمومی تعریف‌شده کپی می‌شود؛ قبل از هر خروجی، فایل‌های جدید در این مسیرها را بررسی کنید و هرگز Secret در آن‌ها قرار ندهید.

## نصب آینده روی VPS (فقط پس از اجازه صریح مالک)

- یک زیردامنه جداگانه برای Demo انتخاب کنید. HTTPS معتبر، فایروال و Nginx به‌روز لازم‌اند. پورت دیتابیس را عمومی نکنید.
- فقط بسته خروجی و checksum را منتقل و صحت آن را تأیید کنید. مخزن Git، backend، فایل‌های `.env` و تنظیمات سرور را در ریشه وب قرار ندهید.
- فایل نمونه `ops/nginx-demo.conf.example` را پس از جایگزینی دامنه، مسیر گواهی TLS، ریشه عمومی و فایل htpasswd بررسی کنید. Basic Auth باید کل Demo (هر دو رابط در یک origin) را محافظت کند. فایل رمز هش‌شده را خارج از web root و با دسترسی محدود بسازید؛ رمز را در Git ذخیره نکنید. HTTP را فقط به HTTPS هدایت کنید؛ Basic Auth بدون TLS قابل قبول نیست.
- قبل از فعال‌سازی تنظیمات، `nginx -t` اجرا شود. پس از فعال‌سازی مجاز، HTTP 401 بدون اعتبارنامه، پاسخ 200 برای صفحات با اعتبارنامه، پاسخ 404 برای API و مسیرهای داخلی، و headerهای CSP/noindex بررسی شوند. دسترسی مرورگر و مجوز Demo را از طریق دستگاه دیگری نیز آزمایش کنید.
- فایل نمونه به هیچ API خارجی proxy نمی‌کند. Demo نباید به‌عنوان پنل مدیریت واقعی استفاده شود. برای بازگشت، نسخه قبلی بسته و تنظیمات را نگه دارید و فقط پس از اعتبارسنجی نسخه جدید مسیر سرویس را تغییر دهید. پس از ارائه در دستگاه مشترک، داده‌های مرورگر و Service Worker را پاک کنید.

در بسته خصوصی، robots در HTML مشتری نیز noindex است. Service Worker خروجی خصوصی فقط Cacheهای قدیمی برنامه را پاک می‌کند و هیچ درخواست یا پاسخ احراز هویت‌شده‌ای را کش نمی‌کند؛ قابلیت PWA آفلاین در سورس عمومی حفظ شده، اما در بسته خصوصی عمداً غیرفعال است. برای Demo از زیردامنه تازه استفاده کنید تا کش/نشست قبلی روی همان origin وجود نداشته باشد.

`robots.txt` و `X-Robots-Tag` صرفاً دستور به خزنده‌ها هستند و امنیت ایجاد نمی‌کنند؛ احراز هویت و TLS الزامی‌اند. فونت‌های Google در صورت دسترسی بارگذاری می‌شوند؛ بدون اینترنت از fallback استفاده می‌شود. تست کامل سرعت و Core Web Vitals روی VPS پس از نصب مجاز انجام خواهد شد.

## سناریوی ارائه ۵–۷ دقیقه‌ای

۱. صفحه مشتری را با فارسی و عربی (RTL) و انگلیسی و ترکی (LTR) باز کنید؛ دسته‌بندی، جست‌وجو و جزئیات محصول را نشان دهید.
۲. سبد را پر و ویرایش کنید؛ توضیح دهید که ارسال سفارش واقعی نیاز به QR معتبر و Backend دارد. پرداخت موفق ساختگی نمایش ندهید.
۳. در پنل Demo محصول و قیمت را تغییر دهید؛ تب مشتری را مشاهده کنید و ماندگاری بعد از Reload را بررسی کنید.
۴. حالت موبایل و دسکتاپ، فرم‌ها و بازیابی نسخه پشتیبان محلی را فقط با داده نمونه نشان دهید.
۵. محدودیت‌ها را به مشتری توضیح دهید: داده محلی، بدون کاربران/سفارش/پرداخت واقعی، بدون همگام‌سازی چنددستگاهی. تنظیمات تولید، امنیت واقعی و عملکرد آنلاین پروژه جداگانه اعتبارسنجی می‌شوند.

## مسیر Backend واقعی (خارج از دامنه Demo)

مسیر Fastify/PostgreSQL در `backend/README.md` و راهنمای قبلی وجود دارد؛ معادل کامل APIهای commerce در Supabase نیست. قبل از انتخاب VPS برای نسخه عملیاتی باید دامنه امکانات، قرارداد API، schema پایه، migrations، secrets، tenant isolation، backup/restore و callback پرداخت تأیید شوند. اطلاعات واقعی و migrations را بدون اجازه اجرا نکنید.

## وضعیت انتشار GitHub

در مرحله هشتم `main` به `dc624e90705ce15a97b5c59571c858fe4cf9034c` رسید و CI موفق شد. Vercel Git deployment برای دو شاخه main و ux/system-redesign-vq3 غیرفعال شده است؛ GitHub Pages مستقل از آن به‌صورت خودکار اجرا و موفق شد. این وضعیت باید در Settings → Pages بررسی و در صورت عدم نیاز توسط مالک غیرفعال شود. انتشار قدیمی vq.3 تغییر داده نشده است. قبل از هر Push/Merge یا انتشار جدید، تمام مسیرهای خودکار را کنترل کنید. سه خطای smoke محیط واقعی (DNS/HTTP 404) همچنان باز هستند و نباید با حذف تست‌ها پنهان شوند.

## کنترل انتشار پیش از ثبت مرحله نهم

Workflow قدیمی انتشار vq.3 در اصلاحات مرحله نهم فقط دستی (workflow_dispatch) می‌شود؛ تگ موجود تغییر نمی‌کند. این اصلاح جایگزین تنظیمات GitHub Pages نیست. مالک در Settings → Pages → Build and deployment باید Source را غیرفعال کند (در صورت نمایش گزینه None یا Unpublish site). پس از آن، CI روی شاخه مستقل و خروجی export خصوصی اجرا شود؛ هیچ VPS یا دامنه‌ای فعلاً لازم نیست.
