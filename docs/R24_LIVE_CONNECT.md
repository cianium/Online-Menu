# R24.8 — Live transport candidate (not enabled)
The SQL in docs/sql/R24_CONNECT_REVIEW.sql is a review draft, deliberately outside the migration directory. No database has been changed. Generate a migration with the Supabase CLI in an isolated development environment, run the tenant/revocation/concurrency/privilege tests and advisors, and verify Edge Function types before enabling. The CLI and PostgreSQL are not available in this environment.
The existing order and admin Edge Functions provide guarded routes. Both default to disabled unless ROMANO_CONNECT_ENABLED=true. Guest identity is the individual table-session token, never a table ID, member phone or shared table-session ID. A domain-separated binding is returned on a new QR scan; subsequent chat requests require that binding and the matching HttpOnly cookie. Keep the binding in sessionStorage only. Existing ordering and public menu routes remain unchanged. Admin routes reuse server-side verified active session, CSRF and manager membership; the SQL checks membership again. There is no cross-device demo fallback. No broadcast channel has been exposed.
Candidate limits: one conversation per token, 200 messages per conversation, 10 messages per sender kind per 10 seconds, 50 recent conversations per inbox read, staff read window 24h after expiry. These are limits, not a deletion schedule. Actual storage retention/cleanup, session revocation race tests, rate limiting of scan and read traffic, pagination and load testing are release blockers. Connected order linking is intentionally not implemented because orders currently belong to a shared table session, not the individual guest token. Existing physical location foreign keys are retained as internal compatibility; live chat refuses ambiguous active locations. Manager self-assignment only; employee directory not implemented.
Initial transport is authenticated polling, not WebSocket push. Never advertise presence/read receipts until backed by verified data. Supabase private-channel design remains a future improvement and needs a separate guest authorization design.
