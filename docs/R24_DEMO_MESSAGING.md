# R24.4 — Local demo messaging
The R24.3 page-memory preview is replaced with IndexedDB (one conversation aggregate per record). The guest's opaque conversation/guest identifiers are tab-session scoped, retained on refresh, rotated on branch/table or membership changes and explicit new conversation. This is NOT authentication: same-origin scripts and developer tools can inspect browser storage. Tab duplication may copy sessionStorage. Do not use real customer data.
Each send uses one readwrite transaction, rereads the latest version, applies core idempotency and returns only after commit. Staff command APIs support list/read/assign/reply/resolve/close subject to domain roles; real staff UI and membership authorization are R24.5/R24.8. BroadcastChannel carries only a change hint, and the open customer dialog polls every two seconds as fallback. No cross-device or network delivery.
Limits: four-hour conversation TTL; 100 records per origin, expired records older than 24 hours after expiry pruned on new record creation. Retention is lazy, not a guaranteed deletion deadline. Full records are validated before use; storage failure does not fall back to memory. New conversation retains old records for staff history until pruning. Browser quota and disabled storage produce explicit errors. No migration of ephemeral R24.3 messages.
No verified table/order identifiers are attached until R24.6. Messages ready for same-origin staff inbox integration. Browser tests of actual IndexedDB and cross-tab events are required; memory-transaction test doubles exercise core adapter behavior but are not proof of browser concurrency.

Follow-up: profile identity contributes to guest scope; order-only membership notifications no longer rotate a conversation. Refreshes cannot replace newer displayed versions. Browser regression scenario covers persistence on reload, same-origin staff reply and independent guest session; execution is still required.
