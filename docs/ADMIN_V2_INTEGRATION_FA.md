# ارزیابی و برنامه ادغام انتخابی admin-v2

## وضعیت این تغییر

این سند نتیجه بررسی سه ورودی است:
- مخزن جاری: `cianium/Online-Menu`، شاخه `main`، commit مبنا `13b9bd5e0055e176fbf33f2955f915995de98ea9` (vq.3).
- آرشیو منابع `Online Menu.zip`؛ شامل بسته Romano 5.0 Phase 1 و نسخه پایه 4.9.1.
- آرشیو مرجع `admin-v2.zip`.

این commit فقط مستندات تصمیم‌گیری و QA را تغییر می‌دهد؛ فایل‌های اجرایی، schema دیتابیس، مسیرهای API، تنظیمات انتشار و منوی مشتری عمداً دست‌نخورده‌اند.

## تصمیم معماری

مبنای توسعه، مخزن Online-Menu vq.3 است. آرشیو Romano 4.9.1 / 5.0 Phase 1 مرجع تاریخی و مقایسه‌ای است، نه مبنای جایگزین. بسته 5.0 Phase 1 در ساختار منابع، نسخه اجرایی جداگانه‌ای از 4.9.1 ارائه نمی‌کند و نباید صرفاً بر اساس نام نسخه، قابلیت جدیدی به آن نسبت داده شود.

پنل فعلی vq.3 از قبل موارد زیر را دارد:
- داشبورد و وضعیت سلامت منو
- مدیریت محصولات، دسته‌ها و محتوای چندزبانه
- ورود مدیر و اتصال API
- سفارش‌ها و KDS با کنترل نسخه وضعیت سفارش
- شعبه‌ها، میزها، QR امضاشده و تنظیمات درگاه
- بارگذاری رسانه از مسیر سرور

پس انتقال دوباره صفحات مشابه از admin-v2 باعث تکرار منطق و ریسک regression می‌شود.

## ارزیابی admin-v2

### الگوهای قابل استفاده به‌عنوان مرجع طراحی
- گروه‌بندی روشن ناوبری و سلسله‌مراتب صفحات
- الگوی کارت‌های خلاصه و جدول‌های قابل مرور
- جست‌وجو و فیلتر در جدول‌ها
- فرم‌های گروه‌بندی‌شده، Modal و پیام وضعیت
- توجه به چیدمان موبایل

این الگوها باید با سیستم بصری موجود RAMEN، کامپوننت‌های فعلی و زبان فعال تطبیق داده شوند؛ انتقال مستقیم CSS یا پوسته کامل توصیه نمی‌شود.

### مواردی که نباید از آرشیو کپی شوند
- داده‌های ثابت داشبورد، کاربران، سفارش‌ها، درآمد و تراکنش‌ها
- فرم‌های `data-demo-form` که فقط پیام موفقیت نشان می‌دهند و ذخیره واقعی ندارند
- اعلان‌های ساختگی و وضعیت آنلاین ثابت
- صفحه‌های مالی/کاربران/نقش‌ها تا زمانی که API و مجوز واقعی آن‌ها موجود و تست نشده باشد
- کد Toast که پیام را با `innerHTML` وارد DOM می‌کند؛ این الگو در صورت ورود متن کنترل‌نشده می‌تواند XSS ایجاد کند
- فونت‌ها، آیکون‌ها یا وابستگی‌های تکراری بدون نیاز روشن

## تطبیق قابلیت‌ها با Backend فعلی vq.3

کد `supabase/functions/romano-admin/index.ts` در مخزن شامل موارد زیر است:
- احراز هویت Supabase و مدیریت نشست با Cookieهای HttpOnly
- کنترل CSRF و Origin
- عضویت رستوران و نقش‌های owner / manager / editor / viewer
- خواندن داده tenant-scoped
- کنترل نقش برای تغییر وضعیت سفارش، شعبه، میز و تنظیمات درگاه
- ذخیره snapshot منو و بارگذاری رسانه از مسیر سرور

با این حال، وجود این کد به معنی تأیید deploy شدن Function، secrets، schema و مسیرهای واقعی Production نیست.

در endpointهای بررسی‌شده، API مدیریتی کامل برای دعوت/تعلیق کاربران، ویرایش نقش‌ها، گزارش‌های تحلیلی و دفتر تراکنش عمومی مشاهده نشد. بنابراین صفحه‌های users/roles/analytics/finance در admin-v2 نباید به شکل fake UI به محصول افزوده شوند.

## نقشه اجرای پیشنهادی

### P0 — پیش از افزودن ماژول‌های جدید
1. تطبیق migrationهای Supabase با schema محیط هدف و بررسی ترتیب اجرای آن‌ها.
2. تأیید routeهای Vercel برای `/api/v1/auth/*` و `/api/v1/admin/*` به Function صحیح.
3. اجرای آزمون احراز هویت، انقضای نشست، refresh، logout و CSRF.
4. آزمون جداسازی tenant با دو رستوران مستقل و شناسه‌های متقاطع.
5. آزمون نقش‌های viewer/editor/manager/owner برای تمام عملیات حساس.
6. آزمون کامل مشتری، ادمین، سفارش، KDS و callback پرداخت در محیط staging.

### P1 — تکمیل مدیریت تیم
1. طراحی مدل دعوت و عضویت، بدون نمایش ایمیل/اطلاعات حساس کاربران دیگر.
2. API سمت سرور برای دعوت، لغو عضویت و تغییر نقش با کنترل مالکیت tenant.
3. ثبت audit برای تغییرات دسترسی و نمایش رویدادهای واقعی.
4. رابط چهارزبانه برای کاربران و نقش‌ها؛ هیچ مجوزی صرفاً در JavaScript enforce نشود.

### P1 — گزارش و مالی
1. تعریف قراردادهای read-only برای آمار فروش و تراکنش‌ها از داده معتبر سفارش/پرداخت.
2. تفکیک مبلغ سفارش، مبلغ پرداخت‌شده، برگشت/ناموفق و وضعیت نیازمند reconciliation.
3. فیلتر تاریخ، شعبه و وضعیت با timezone رستوران.
4. نمایش حالت خالی و خطا به‌جای صفر یا داده نمونه.

### P2 — Backup و Restore
1. نمایش فقط وضعیت Backup واقعی و شناسه/زمان اجرای آن.
2. تهیه نسخه سازگار با schemaVersion و tenant.
3. محدودکردن Restore به مالک/مدیر مجاز، با تأیید دوباره و audit.
4. تست بازیابی در محیط جدا؛ هرگز اجرای آزمایشی روی داده Production انجام نشود.

## معیارهای پذیرش

- همه متن‌های UI در fa/en/tr/ar ترجمه شده باشند.
- `lang` و `dir` متناسب با زبان تغییر کند؛ فارسی و عربی RTL، انگلیسی و ترکی LTR.
- در موبایل هیچ جدول یا فرم باعث overflow افقی کل صفحه نشود.
- هیچ آمار، کاربر، پرداخت یا رویداد ساختگی در پنل واقعی نمایش داده نشود.
- تمام عملیات حساس با مجوز سمت سرور و tenant scope اجرا شوند.
- هیچ Secret یا توکن دسترسی در localStorage، HTML یا log مرورگر قرار نگیرد.
- تست‌های مشتری و ادمین و مرورگر قبل از ادغام PR اجرا شوند.

## وضعیت فعلی انجام کار

- شاخه مستقل `feat/admin-v2-curated-integration` از commit مبنا ایجاد شده است.
- این مرحله فقط مستندات و QA را ثبت می‌کند.
- هیچ قابلیت نمایشی از admin-v2 به محصول منتقل نشده است.
- هیچ migration، Secret، تنظیمات Vercel یا داده Production تغییر نکرده است.
- ادغام به main و انتشار Production انجام نشده است.

این محدودسازی عمدی است: افزودن صفحات مالی/کاربران با داده ساختگی یا مجوز سمت مرورگر، کیفیت و امنیت محصول را پایین می‌آورد.
