# تصمیم ادغام انتخابی admin-v2 — جمع‌بندی مرحله هشتم

مرجع تاریخی: [PR #17](https://github.com/cianium/Online-Menu/pull/17)، شاخه `feat/admin-v2-curated-integration`، commit `68f9ea7e54d14d62aa830ec6c1b01769fb363365`. این سند جمع‌بندی به‌روز یافته‌های آن PR است، نه انتقال عین فایل. اصل سند در شاخه مرجع محفوظ است.

## مبنا و تصمیم

مبنای اجرایی، vq.3 در `ux/system-redesign-vq3` است. آرشیو Romano 4.9.1/5.0 Phase 1 و admin-v2 فقط مرجع هستند؛ بسته 5.0 Phase 1 در منابع، نسخه اجرایی مستقلی از 4.9.1 ارائه نمی‌کند. پنل vq.3 از قبل داشبورد، مدیریت محصول و دسته‌بندی و ترجمه، ورود، سفارش و KDS، شعبه، میز، QR امضاشده، تنظیمات درگاه و بارگذاری رسانه دارد. انتقال کامل پوسته admin-v2 باعث تکرار و ریسک رگرسیون است.

از admin-v2 تنها الگوهای گروه‌بندی ناوبری، کارت‌ها، جداول، فیلتر، فرم و پنجره، پیام وضعیت و چیدمان موبایل به‌عنوان مرجع طراحی استفاده شود. فرم‌های `data-demo-form` صرفاً نمایشی، داده‌های ثابت درآمد/کاربر/تراکنش، اعلان ساختگی، وضعیت آنلاین ثابت و Toast مبتنی بر `innerHTML` نباید وارد محصول واقعی شوند. وابستگی و CSS تکراری افزوده نشود.

## جداسازی Demo و Production

Demo محلی فقط از داده نمونه و localStorage استفاده می‌کند و جایگزین احراز هویت یا پرداخت واقعی نیست. در مسیر Production، کد Admin Function شامل Cookie HttpOnly، CSRF و Origin، عضویت رستوران، نقش‌های owner/manager/editor/viewer، کنترل tenant و عملیات سفارش، شعبه، میز، درگاه، snapshot و رسانه است. وجود کد یا موفقیت تست mock به معنی تأیید استقرار واقعی نیست.

مدیریت دعوت/تعلیق کاربران و نقش‌ها، گزارش‌های مالی و تحلیل فروش، دفتر تراکنش عمومی و backup عملیاتی تا تکمیل قرارداد API و مجوز واقعی نباید به صورت UI ساختگی به محصول اضافه شوند.

## اقدامات پیش از Production

- تطبیق baseline دیتابیس و migration history محیط هدف، و صحت rewriteهای Vercel برای auth/admin.
- آزمون ورود، نشست، refresh/logout و CSRF؛ آزمون tenant متقاطع و همه نقش‌ها در staging؛ بررسی سفارش، KDS، callback پرداخت و reconciliation.
- سپس طراحی دعوت/عضویت و audit با کنترل tenant؛ گزارش read-only از داده معتبر با timezone شعبه و تفکیک مبلغ سفارش، پرداخت، برگشت و خطا.
- Backup/Restore واقعی با schemaVersion، tenant، مجوز، تأیید مجدد و audit؛ تست بازیابی در محیط جداگانه، نه Production.
- معیار پذیرش: fa/en/tr/ar و dir/lang صحیح، عدم overflow، عدم آمار جعلی، کنترل مجوز سمت سرور، عدم نگهداری Secret در مرورگر و اجرای QA کامل.

Migrationهای Supabase فعلی عمدتاً افزایشی‌اند و bootstrap کامل جداول پایه users، restaurant_memberships، restaurants، categories، products و ترجمه‌های آنها تأیید نشده است. migrationهای Fastify را نباید بدون تطبیق به Supabase منتقل کرد. پیش از هر DDL باید baseline واقعی بررسی شود. اتصال Vercel و Supabase پروژه هدف در ممیزی قبلی قابل تأیید نبود؛ این دلیل اثبات خرابی Production نیست.
